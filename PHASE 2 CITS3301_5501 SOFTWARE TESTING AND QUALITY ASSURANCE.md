##  1\. Task 1 – Prototype

For the prototype, I built on the Java starter code. It loads the policy index page, pulls out all the links with jsoup, and keeps the ones that look like policy documents. I decided this based on the file extension: anything ending in .pdf, .doc, .docx, .rtf or another common office format counts. I also removed duplicate links, because the same document sometimes appears more than once on the page or with a \# on the end.

It then downloads the first five documents and prints some basic information about each one: the URL, the HTTP status, the content type the server says it’s sending, the file size, and the first few bytes of the file. The first bytes are useful because PDFs start with %PDF and newer office files start with PK, so they give a quick sanity check that the file is what it claims to be. The files aren’t saved. All requests go through the starter’s fetch() method, so the run stays under the 20-request limit with a delay between requests. A normal run makes 6 requests in total.

When I ran it against the live site, it found 217 links that looked like policy documents. All five downloads came back as 200 OK with application/pdf and started with %PDF.

To keep the prototype simple, I assumed that every policy document is linked directly from the index page and that the file extension is enough to tell whether something is a document.

The prototype has a few limitations. First, relying on file extensions isn’t very reliable. It would miss documents whose URLs don’t end in an extension, and it also picked up a link to a different website ([www\.uwa.edu.au](http://www.uwa.edu.au)) just because it ended in .doc. Second, it always takes the first five links on the page, so in my test run it only ever downloaded PDFs and never checked any of the Word or RTF files. Third, checking the first few bytes only shows that a file starts correctly, not that it actually opens; a corrupt PDF would still pass. Finally, there’s no retry logic, so if a request times out or the server returns an error, it’s simply reported as a failure.

## 3\. Task 3 \- Fixtures and Test Doubles for a Policy-Document Scraper

A Java scraper could find and download policy documents linked from [https\://uwa-policy.cits5501.arranstewart.io/policy/](https://uwa-policy.cits5501.arranstewart.io/policy/)  To test it reliably, we need examples and server responses that we can control. 

### 1\. Repeatable Testing Using Fixtures

Fixtures are saved examples with known expected results. A saved index page could contain known policy links and the element or value the scraper expects. Modified copies could remove that element, move it, or replace its value. The expected result is an extraction error and no saved result, rather than empty, partial, or mismatched data being treated as valid. To represent a truncated page, a local server could declare a \`Content-Length\` larger than the HTML body it actually sends. The scraper should report the incomplete response and return no result.

Saved valid PDF and office files show what successful downloads look like. An HTML page at a PDF URL and a corrupt PDF show two different files the scraper should reject. A local HTTP server can serve these inputs with chosen status codes and headers. Tests can compare the links, bytes, and errors actually produced with the expected results. Because the test data stays the same, changes to the live website do not change the test outcome.

2\. Investigation of Website Request Limits

I used \`curl\` to request the policy index and save its headers and HTML. One request reached the website. It returned HTTP 200, \`Content-Type: text/html; charset=utf-8\`, and 584,187 bytes of HTML. The page contained links to PDF, DOC, and DOCX files. I made no policy-document download requests.

The response included \`Retry-After: 10\`, \`X-RateLimit-Limit: 3\`, \`X-RateLimit-Remaining: 2\`, and \`X-RateLimit-Reset: 1792209109\`. These headers suggest that the site has a request limit or delay, but they do not show whether it limits document downloads. I stopped after seeing \`Retry-After\`. This response was not HTTP 429, 403, or 503, and I have no repeated-download results from which to measure a limit. If live requests are restricted, further scraper tests can use saved responses and a local server.

3.Simulating Network Failures Using Test Doubles

Test doubles can supply responses without using the live website. WireMock can return error codes, delay a response beyond the proposed 7-second timeout, or cause connection faults. OkHttp MockWebServer can queue responses, send a body very slowly, or close a connection before or during a download. A delayed endpoint could check that one timed-out request stops within its limit. Three failed responses could check that the scraper makes exactly three attempts, with waits increasing by 2 seconds between retries, then reports failure and returns no result. Java's built-in \`HttpServer\` is enough for simple local responses; custom handlers can also send fewer bytes than the declared \`Content-Length\`. These options are described in the \[WireMock fault guide\](https\://wiremock.org/docs/simulating-faults/), \[MockWebServer socket policies\]([https\://square.github.io/okhttp/5.x/mockwebserver3/mockwebserver3/-socket-policy/index.html](https://square.github.io/okhttp/5.x/mockwebserver3/mockwebserver3/-socket-policy/index.html))  and \[JDK \`HttpServer\` documentation\]([https\://docs.oracle.com/en/java/javase/17/docs/api/jdk.httpserver/com/sun/net/httpserver/HttpServer.html](https://docs.oracle.com/en/java/javase/17/docs/api/jdk.httpserver/com/sun/net/httpserver/HttpServer.html)).

Separate local responses could check the group's error rules: a 403 or 404 page should be reported as a client error after one attempt, while a 502 or 503 page should be reported as a server error and retried up to three attempts with the same increasing backoff. Neither HTML error page should be parsed as policy data. JUnit could run these checks; Mockito could make a replacement HTTP-client interface return data or throw an exception in a unit test. Mockito would not test a real network connection. These are proposed tests. The only implemented test double is the small \`HttpServer\` used below; no scraper has been run against these failure cases.

4\. Demonstration of a Failure Fixture

We created \`fixtures/invalid-policy.pdf\` for this demonstration; it did not come from the policy website. Despite its name, the 486-byte file is an HTML page saying that the document is temporarily unavailable. It starts with \`\<\!DOCTYPE html\>\`, not the PDF signature \`%PDF-\`. This saved file is the fixture: every run uses the same known invalid content.  
\`FixtureServer.java\` stands in for the website. When it starts, it reads the local fixture with \`Files.readAllBytes\` and starts Java's \`HttpServer\` on \`127.0.0.1:8765\`. For \`http\://127.0.0.1:8765/invalid-policy.pdf\`, it sends HTTP 200, \`Content-Type: application/pdf\`, and a PDF filename in \`Content-Disposition\`, then writes the HTML bytes it read. The URL and headers look like a successful PDF download, but the content is HTML. This reproduces the group's HTML-at-a-PDF-link case. It does not test a corrupt PDF that has PDF-like bytes but cannot be opened; that needs a separate fixture.

We compiled and ran the server, then fetched the URL with \`curl\`. The response was HTTP 200 with \`application/pdf\` and 486 bytes. The downloaded bytes matched the fixture, and the local \`file\` utility identified them as HTML. In a scraper test, the scraper would request this local URL and check the downloaded bytes for \`%PDF-\`. The test would expect an invalid-content error, no result, and no saved PDF. We have not run a scraper against it. Creating this exact response on the real website would require control over the site or an unpredictable fault, so the local fixture makes the test repeatable without adding traffic to the site.

## 4\. Task 4 \- Adversarial inputs

The following test cases are designed to identify assumptions made by another team’s web scraper. Different inputs and unexpected situations are used to check whether the scraper handles errors correctly without crashing or producing incorrect results.

| idea | Assumption being challenged | Test input / environment | Failure \+ detection |
| :---- | :---- | :---- | :---- |
| 1 | Downloaded files will always be a reasonable size | Provide an extremely large downloadable file | The scraper becomes very slow, freezes, crashes, or uses excessive memory |
| 2 | Policy documents will only use the file formats the scraper expects | Provide a valid policy document in an unsupported or unexpected format, such as .odt | Scraper ignores valid documents or fails when processing it. |
| 3 | A file ending in .pdf is actually a real PDF | Make a link called policy.pdf but have it return HTML instead | The scraper wrongly accepts/saves it as a PDF instead of detecting the mismatch |
| 4 | Document links will always have simple normal names | Use a link with spaces or special characters, e.g. policy%20final(1).pdf | The scraper crashes, builds the URL incorrectly, or fails to download the file |
| 5 | Every document link on the website will be unique | Add the same PDF link multiple times on the webpage | The scraper downloads the same file repeatedly instead of identifying duplicate links |
| 6 | Document links will always contain URLs | Provide a relative link such as ../document/policy.pdf instead of full URL | The scraper fails to build the correct URL or cannot download the  document |
| 7 | The server will always send the complete file | Make the server stop sending data halfway through a PDF download | The scraper accepts an incomplete file as successful instead of detecting the missing data |
| 8 | Document links will always lead directly to the file  | Make a PDF link redirect to a login page instead of the document | The scraper saves the login page as a PDF or reports the download as successful without checking the content |

These tests help identify possible weakness in the scraper when handling unusual inputs and unexpected website behaviour. Testing these situations can help improve the scraper’s reliability and ensure errors are detected and reported correctly.
